# Textify 목적 분석과 기반 개선

검토일: 2026-09-07

## 제품의 목적과 판단 기준

Textify의 목적은 사진 한 장을 오프라인에서 ASCII/유니코드 텍스트 그림으로 바꾸어 복사·공유·저장할 수 있게 하는 것이다. `PRODUCT_SPEC.md`의 핵심 사용자 작업은 “사진을 텍스트 기반 그림으로 바꿔서 바로 쓰기”다. 사진 선택, 첫 결과, 옵션 조정, 내보내기, 최근 작업이라는 하나의 흐름이 제품의 중심이다.

가장 중요한 품질 기준은 다음과 같다.

1. 지원되는 일반 사진으로 첫 결과를 얻을 수 있어야 한다.
2. 사용자의 마지막 옵션이 결과에 반영되어야 한다.
3. 화면의 결과, 내보낸 결과, 최근 작업의 결과와 옵션이 일치해야 한다.
4. 사진과 생성 내용은 기기 안에서 처리해야 한다.

기존 App → TextifyUI → TextifyKit 구조와 서비스 주입은 이 목적에 적합하다. 이번 개선에서는 구조 전체를 교체하거나 네트워크/계정 기능을 추가하지 않고, 이 기준을 깨뜨리는 입력·생성·기록 경계를 수정했다. 읽기 전용 제품·코어 검토와 사진 입력 개선은 `gpt-6-astra`/`high` 워커에 배정했다. 실행 속도 인자는 제공되지 않았다.

## 확인한 문제와 구현

| 경계 | 변경 전 문제 | 변경 후 동작 |
|---|---|---|
| 사진 입력 | 원본 해상도로 읽은 이미지를 코어가 한 변 4096픽셀 초과로 거부했다. 회전 사진은 전체 크기 비트맵을 다시 그렸다. | ImageIO에서 방향/미러를 적용하며 긴 변 최대 4096픽셀로 디코딩한다. 작은 이미지는 크기를 유지한다. |
| 옵션 반영 | throttle 미리보기, debounce 최종 생성, 내부 생성 작업이 분리되어 있었다. 화면 이탈은 생성 작업만 취소했고, 폭의 마지막 값은 편집 종료 이벤트에 의존했다. | 예약 지연과 변환을 하나의 소유 작업으로 관리한다. 폭은 50ms, 다른 옵션은 200ms 후 마지막 값을 생성하며 편집 종료 시 즉시 생성한다. 취소는 예약과 실행 양쪽에 적용된다. |
| 결과 상태 | 화면에 남은 이전 결과를 현재 편집 옵션으로 설명하고 내보낼 수 있었다. | 완료 결과와 생성 당시 옵션을 함께 보관한다. 결과 설명은 완료 옵션을 표시하며 현재 옵션이 반영되기 전에는 복사·공유·저장을 비활성화한다. |
| 최근 작업 | 복사 후 비동기 기록이나 사진 저장 완료 시 현재 결과/옵션을 다시 읽어 실제 내보낸 결과와 달라질 수 있었다. | 액션 시작 시 완료 결과의 히스토리 요청을 캡처한다. 저장 중 새 결과가 생성되어도 캡처한 요청을 기록한다. |
| 기록 실패 | 실패를 로그에만 남겼고 기록 중/성공의 중복 방지 상태가 섞여 있었다. | 기록 중인 키와 마지막 성공 키를 구분한다. 내보내기 성공과 최근 작업 실패를 따로 알리고 재시도를 허용한다. |

기존 `Throttler`/`Debouncer` 사용 경로와 미리보기용 중복 생성 코드를 제거했다. `GenerationTaskManager`의 작업은 `@MainActor`를 명시하고, 실제 이미지 변환은 기존 `TextArtGenerating` 경계를 유지한다. 외부에서 `textArt`를 임의로 바꾸는 setter는 제거했다. 테스트는 생성기 주입으로 결과를 준비한다.

## 검증 기록

- 기준 `make build-app`: 성공.
- 변경 후 `make test-app`: 성공. Swift Testing 기준 **TextifyKit 50개 + TextifyUI 46개 = 96개** 테스트 통과.
- 새 회귀 테스트: ViewModel 9개, 사진 입력 3개 테스트 선언. 사진 테스트는 EXIF 8방향과 큰 사진 2방향을 인자로 각각 실행한다.
- 검증한 동작: 예약 생성 취소, 취소를 무시하고 늦게 끝나는 이전 생성, 부모 Task 취소 전파, 편집 종료 이벤트 없는 폭 조절, 이전 결과 내보내기 차단, 저장 도중 새 결과 생성, 복사 직후 옵션 변경, 기록 실패 후 재시도.
- 최종 독립 검토에서 옵션 생성 실패 후 재시도 UI 부재를 발견하여, 오류 알림을 닫아도 남는 실패 상태와 현재 옵션 재시도 버튼을 추가했다. 이전 결과 보존 → 새 옵션 실패 → 동일 옵션 재시도 성공 회귀 테스트를 추가했다.
- 최종 `make build-app`: 성공.
- 사진 검증: 작은 JPEG/PNG 유지, 잘못된 데이터 오류, EXIF 회전/미러의 픽셀 위치, 5000×1000 입력의 축소 후 실제 코어 생성, 4096픽셀 경계.
- Swift Intelligence: 저장소 루트의 스킴 조회는 `No .xcworkspace or .xcodeproj found in workspace_path`로 실패하여 실제 Xcode 루트인 `TextifyApp`을 사용했다. 최초 심볼 조회는 `Xcode index store is missing for scheme TextifyApp` 및 워커의 `TextifyKit` 인덱스 부재로 실패했지만, 기준 빌드 후 `TextifyApp` 스킴의 심볼 조회가 성공했다. 수정 ViewModel 진단은 `[]`였다.
- 첫 통합 빌드는 사진 서비스의 `SwiftUI` import 제거로 `Cannot find type 'PhotosPickerItem' in scope` 오류가 발생했다. import 복원 후 전체 테스트가 통과했다. SourceKit의 빈 진단과 실제 빌드 증거를 구분한다.
- XcodeGen 재생성도 실행했다. 생성 과정에서 기존 서명 설정이 삭제되는 변경은 복원했고, 프로젝트 파일에는 제거한 소스의 참조 삭제만 유지했다.

`TextifyUITests`라는 이름의 타깃은 화면 터치 자동화가 아닌 ViewModel/서비스 단위 테스트다. Simulator 테스트 통과를 실기기 사용성 검증으로 간주하지 않는다.

## 남은 한계와 후속 우선순위

1. **실제 사진 선택부터 내보내기까지의 수동 검증**: 실기기 HEIF/HDR/48MP, PhotosPicker와 iCloud 사진 다운로드, 사진 저장 권한, 복사·공유 수신 앱에서의 정렬 확인이 필요하다. 이번 테스트의 큰 사진은 합성 JPEG이며, 실기기 메모리나 처리 시간은 측정하지 않았다. 3초/500ms 제품 목표 달성을 주장하지 않는다.
2. **투명 이미지의 합성 정책**: 기존 `ImageProcessor`는 alpha 없는 검정 바탕에 그린다. 검정 피사체와 완전 투명 배경이 모두 그레이 값 0으로 합쳐지는 문제를 실제 코어 소스로 재현했다. 투명 로고·선화를 지원하려면 배경 합성 정책과 시각 검증이 필요하다. 이번 변경에는 포함하지 않았다.
3. **미사용 코어 캐시 API**: `prepareCache`가 0.5 보정으로 만든 80×40 버퍼를 `generateWithCache`가 보정 1.0 요청에도 재사용해 일반 생성의 80×80과 달라지는 문제를 재현했다. 현재 앱은 이 API를 호출하지 않는다. 활용 전에 캐시 키/비율 정책을 고치거나 API 범위를 줄여야 한다.
4. **출시 검증**: 사용자 대상 화면 자동화, 성능 측정, 스토어 자산·개인정보/지원 URL·실기기 QA는 기존 배포 점검표의 별도 작업으로 남는다.

변경은 로컬 작업 트리에 있으며 커밋·푸시·실기기 설치·배포는 이 작업의 완료 증거에 포함하지 않는다.
